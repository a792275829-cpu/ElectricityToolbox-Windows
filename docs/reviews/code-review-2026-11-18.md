## 问题与证据

### R1 · P2 · 强制重传把旧状态当作本次导入结果

[upload_daily_report.py:1447](../../集团每日上传/upload_daily_report.py#L1447)

`run_api_upload` 已持有上传前的状态，但没有传给 `confirm_daily_import`。强制重传时，旧记录本来就是 `dataStatus=1` 且带更新时间。只要 POST 返回 `T200/data=[]`，第一次回读仍是旧记录也会判为成功，随后创建日报。

隔离执行实际 `run_api_upload(force=True)`。查询前后均返回同一条完成记录（2026-11-16 09:00:00），代码提交一次、查询两次、调用创建日报一次，并输出“导入成功”。建议用服务端作业标识或可验证的状态变化确认本次提交。无法区分时应提示待核对。

### R2 · P2 · 集团上传暂存回写覆盖原目录外部修改

[upload_service.py:39](../../电力工具箱/toolbox/upload_service.py#L39)

临时文件生成有指纹和提交检查。桌面实际上传完成后用 `copy_upload_file` 直接复制回原目录，最终目标未参与这些检查。上传期间保存原目录同名文件的内容会丢失。以只选能销文件的默认路径验证，在模拟上传期间创建原目录的同日省内表，A1 写入 `external`，暂存产物 A1 为 `generated`。任务返回后重新打开原目录文件，A1 已变成 `generated`。

建议在启动暂存前记录最终目标是否存在及内容指纹，在同目录暂存并原子替换前重新核对。遇到冲突应保留双方文件，同时独立报告已知的远端状态，避免把本地回写问题误当成上传失败。

### R3 · P2 · D 日均价比较接受其他日期的快报

[company_clearing_xlsx.py:1308](../../南方分公司电力市场日报/gd_power_report/company_clearing_xlsx.py#L1308)

新增的 D 日对比卡片调用 `_date_matched_day_narrative`。没有找到对应日期段落时，该函数直接读备用工作表 A4 或同类段落。外层仅验证工作簿识别出的日期，无法发现备用快报的日期不符。

合成工作簿的“分公司”A2 为 2026-11-16，“新快报”A2 为 2026-11-15，其 A4 价格为 900。实际 `parse_day_ahead_comparison_workbook` 输出日期 2026-11-16，基准价 900。该价格会进入两版报告的日前环比。建议验证备用段落日期与目标日期一致。日期不符或无法确认时，按既有缺值规则处理。

### R4 · P2 · 日报均价涨跌会吸收同句其他指标

[company_clearing_xlsx.py:1889](../../南方分公司电力市场日报/gd_power_report/company_clearing_xlsx.py#L1889)

解析器在价格后的整句余文里按“环比”“较昨日”等词的固定优先级搜索。输入“全省日前均价350元/兆瓦时，机组报价环比上涨20元/兆瓦时。”时返回均价环比 +20。即使在价格后先写“较昨日涨22.57元/MWh”，后面的机组报价“环比”仍使代码选中 +20。

建议只提取与价格直接相连的比较短语，并以短语出现在原文中的位置选择。无法证明归属时保留空值。现有测试覆盖了句号隔开的情况，建议补逗号隔开的另一指标和同句多个比较词。

### R5 · P2 · 私有批量上传把无字段的结果项记作成功

[batch-plan.mjs:200](../../电力工具脚本/private-data-uploader-tool/scripts/batch-plan.mjs#L200)

响应解析检查了外围协议和数组元素是否为对象，但任何没有非空 `detail` 的对象都会计为成功。调用实际 `parseImportResponse({retCode:'T200', data:[{}]})`，得到成功一项，其中日期和数据类型均为空。批上传随后累加此成功数。合法空数组也会直接按请求文件数计成功。后续状态查询只打印概览，并未把状态与本次文件逐项对应。此前评审记录已将无明细列为待核对，当前源码仍为旧实现。

建议校验每条明细的必需字段并与本批文件对应。空数组或不足的明细应保留待核对数量，待有本次提交的可靠证据后再计成功。

### R6 · P2 · 不完整的开机曲线会生成省内表 B2

[upload_daily_report.py:1181](../../集团每日上传/upload_daily_report.py#L1181)

`fetch_startup_max` 仅检查是否存在燃煤、燃气记录，随后从任意长度的 `unitCount` 列表求逐小时总量。无效值会被跳过，重复组被字典覆盖，两类市场中一类缺失仍可提交另一类结果。B2 定义为按完整逐小时曲线得到的最大开机台数，因此部分时点会低估该值。

模拟两次正常协议响应。日前燃煤/燃气仅各一项 `[3]` 和 `[2]`，实时仅各一项 `[2]` 和 `[1]`。生产函数返回 5 并记录为最大值。建议校验请求日中每类市场各有唯一的燃煤、燃气记录，每条 24 点且为有限非负整数，验证后再算最大值。此项是此前恢复清单中仍可在当前源码复现的缺口。

### R7 · P2 · WPS 后续区域预检失败前已写入前面的区域

[wps_excel_to_kdocs_gui.py:1671](../../wps自动/wps_excel_to_kdocs_gui.py#L1671)

写入循环完成当前区域的定位、合并状态和值检查后立即写入，下一轮才检查下一个区域。后续区域在预检阶段失败，前面区域已发生修改，只有整批成功后的显式保存尚未执行。

在隔离 Chromium 中运行生产写入脚本，使用两个区域，第二个区域的 `MergeCells` 不返回。结果为明确的第 2 区域超时，模拟 SDK 记录写入 1 次、保存 0 次。此证据确认了实际写入调用，不假定远程持久化结果。建议对同一文档的所有区域先完成预检再执行写入队列，保留已有的超时与不重放保护。此前评审的统一预检要求仍未落地。
