## 结果与证据（发行前检查）

- `version.py check --tag v0.1.37 --require-notes` 输出 `v0.1.37`；五处版本元数据一致，发布说明已由 `version.py check --release-notes` 导出。
- `git -c core.whitespace=cr-at-eol diff --check` 通过。仓库元数据文件本身为 CRLF，`git diff --check` 的默认规则会把新增行尾的 CR 报成行尾空白；按仓库既有换行口径复核后确认没有真正的行尾空格。
- `tools/run_tests.py full --strict`：155 个模块中 150 个通过、跳过 0，用时 625.4 秒。5 个失败模块为 `test_rust_service`、`test_windows_delta`、`test_windows_update`、`test_windows_update_build`、`test_windows_update_helper`，均在 desktop 组。其中 4 个的 traceback 指向会话注入的批量删除守卫 `sitecustomize.py::_check_bulk_delete_guard` 拦截了 `windows_delta.py` 的临时目录清理；`test_rust_service` 为临时 profile 文件被占用（WinError 32）及并发断言失败。这是首次全量运行的真实结果，不表述为一次性全绿。
- 对上述 5 个模块用统一入口集中复跑：`--module` 指定 5 个模块，5/5 通过，跳过 0，用时 106.2 秒。说明失败来自运行环境的守卫注入与并发占用，不是代码回归；未因复跑通过而改写首次全量结果，也未重复整轮。
- Rust：`cargo test --manifest-path native/price-xlsx/Cargo.toml --locked` 13/13 通过；`cargo test --manifest-path desktop/src-tauri/Cargo.toml --locked` 2/2 通过。首次桌面测试因 `target` 缓存残留源码包解压时的旧绝对路径（嵌套同名目录）导致 build script 读取插件权限文件失败；执行 `cargo clean -p tauri` 移除 208 个文件／202.5 MiB 陈旧缓存后重跑通过，未修改源码。
- `start_source_test.ps1 -Smoke` 输出 `TOOLBOX_SMOKE=OK`，`TOOLBOX_DEPS=OK`。

## 隔离安装验收结果

验收复用 `windows_delta` 的安装、清单与补丁模块，在 Git 忽略的 `dist/acceptance-0.1.37/` 隔离目录执行；HKCU 注册表值先保存后恢复，不涉及用户日常安装目录。

- 全新安装：回读版本 0.1.37，清单 14,941 项；主程序、内置 Python、载荷清单与 Rust 服务均在位。
- 覆盖升级：先装 0.1.36（回读 0.1.36），写入 `state/acceptance-marker.json` 模拟用户数据，再用完整包覆盖；回读 0.1.37，标记文件内容与哈希未变，运行时检查同样通过。
- 补丁实际还原：以真实 0.1.36 安装副本为基准，`clone_installation` + `apply_patch(0.1.36→0.1.37)` 后回读 0.1.37，清单与全新安装逐项完全一致。
- 清单差异：覆盖升级目录比全新安装多 1 项 `payload/runtime/ms-playwright/.links/…`（旧版运行时缓存标记），共有 14,941 项的内容哈希差异为 0、缺失为 0。该额外文件不属于 `_remove_added_bytecode` 容许的 `__pycache__/*.pyc` 范围；真实客户端若存在同类残留，后续增量更新可能按既有逻辑回退完整包。这是已识别的非阻塞差异，本版未改动该逻辑。
- 安装版运行时：内置 Python 3.11.15 成功导入 tkinter／openpyxl／pandas／numpy 并实际创建、销毁 Tk 窗口（`TK=OK`）；Rust 服务实际启动，输出 `service-ready`（protocol 3）与 `service-closed`。

- `state/installed.json` 在静默安装目录中不存在（该文件由首次真实运行时在工作区数据目录生成），本轮未能回读；改为回读三个安装目录的 `payload/manifest.json`，版本均为 0.1.37。此项列入验证边界。
